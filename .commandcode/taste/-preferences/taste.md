# Taste / Preferences
- Expects the assistant to prioritize delivering the actual requested feature over diving into unrelated environment/toolchain problems; gets visibly frustrated when time is spent debugging build infrastructure (e.g., "你在干什么，还没好吗，我要你写个链接发送数据很难吗" after a long AGP/R8 dexing investigation). When blocked by environment issues, state clearly that the code itself compiles/passes and hand back the feature rather than continuing the rabbit hole. Confidence: 0.75
- Wants the answer up front: when a long investigation has been going on, expects a crisp "先说结论" (what's wrong, what was fixed, what to do) followed by concrete actionable steps, not a process narrative. Confidence: 0.6
- Prefers to be taught how to write code — wants step-by-step teaching guidance (principles, file lists, key code, per-step verification) rather than having the assistant implement features directly. Even after a full design plan was approved, the user explicitly said "你教我来写" (teach me to write it myself) — the assistant should explain each layer and leave the writing to the user, then review. Confidence: 0.95
- Prefers to be taught self-service diagnostic/operational routines, not just handed the answer: when asking the assistant to check something (e.g., "你再看看现在PC端ws ip是多少，或者你教我怎么看"), expects the reusable commands plus a "how to check it yourself next time" explanation alongside the result. Confidence: 0.7
- Prefers implementing features incrementally in small, independently verifiable modules (e.g., explicitly asked to start with only the WS/DSH communication module before anything else). Confidence: 0.8
- Communicates in Chinese (Simplified) and expects responses in Chinese. Confidence: 0.8
- Prefers porting/reusing proven code from an existing reference project over writing from scratch; supplied a reference repo and chose the "port into the current project" approach. Confidence: 0.7
- Prefers to scope mobile platform work to Android first, leaving iOS/OHOS shells untouched for later phases. Confidence: 0.7
- Prefers placing new code under the existing package/naming scheme of the current project rather than copying the reference project's package names. Confidence: 0.7
- Prefers keeping project documentation (README + AGENTS.md) up to date as part of implementation work. Confidence: 0.6
- Reports problems at the symptom level with minimal detail (e.g., "为什么我import不出来啊，是网络问题吗" or "链接成功，但是发送不了"), sometimes offering their own guess at the cause, and expects the assistant to diagnose by inspecting the environment directly (source files, running processes, daemon logs, netstat/thread dumps) instead of being handed reproduction details. Confidence: 0.6
- Develops on Windows with Android Studio on a Kotlin Multiplatform/Gradle project, and depends on a local proxy for dependency downloads (google()/mavenCentral() not directly reachable). Packages the APK themselves in the IDE and validates on a physical Android device (a Xiaomi phone), not an emulator. Device↔PC connectivity is either USB (`adb reverse tcp:<port> tcp:<port>`, which drops after the device reconnects and must be re-run) or the phone's hotspot WiFi (the PC joins the hotspot; the app must target the PC's hotspot-adapter IP, and Windows classifies the hotspot as a Public network, so an inbound firewall rule for the port is required before the phone can reach a local server). The assistant's shell on this machine has no admin rights — admin-only steps like firewall rules must be handed to the user as ready-to-paste commands. Confidence: 0.7
- Frames requirements as complete end-to-end user journeys (e.g., "我需要进入pager然后点击连接并且和发送信息接收dsh回复") and expects the whole path to work: a reachable UI entry point, a connect action, sending, and seeing the reply — compiling/laying down backend code is not "done" if the feature is unreachable from the app's navigation or the render path is broken. Confidence: 0.6
- Encapsulates reusable domain knowledge as project-local agent skills under `.agent/skills/<name>/` (SKILL.md + references/ + scripts/, e.g. a dsh-connect protocol spec with a zero-dependency `smoke.mjs`), and expects the assistant to find and read them — treating the skill as the authoritative spec (superseding earlier informal hand-written specs) and running its scripts to verify before designing. Iteratively extends the skill as the service gains capabilities (e.g., sessions, then workspace/session retrieval + permission approval + reasoning) and flags each update tersely ("再看一下更新的skill吧…增加了会话能力" / "你看一下新加的功能，1)…2)…3)…"), expecting the assistant to re-read the latest skill and adapt the client rather than rely on a previously-read version. Confidence: 0.8
- Prefers splitting app UI by responsibility into single-purpose pages rather than one do-everything screen: directed that the home page stay dedicated to connection management/status display, with a separate session page added for sending messages to the PC-side DSH. Confidence: 0.6
